# Architecture

Single activity, Kotlin, Compose for TV. Five dashboard panels use a 1000dp logical canvas scaled to physical width; no 4K wallpaper allocation, runtime blur or network font. The vector mountain backdrop is intentionally simpler than the photographic mockup. App branding comes from installed package banners/icons; demo app tiles use text.

- `data/Models.kt`: immutable entities, configuration, sample states, unit conversion.
- `data/ConfigJson.kt`: shared configuration codec used for persistence and the phone setup protocol.
- `data/SettingsStore.kt`: private JSON configuration and AES-256/GCM access-token encryption using Android Keystore. Replacement tokens and configuration are committed atomically. Backups are disabled. Tokens never enter saved Compose state, URLs or logs. A saved token cannot be reused for a changed server URL without re-entry.
- `data/AppCatalog.kt`: Leanback/standard launch intent discovery, package visibility queries and HDMI passthrough inputs. No QUERY_ALL_PACKAGES, Play Services or package install permission.
- `ha/HomeAssistantClient.kt`: one authenticated WebSocket. Subscribe before requesting a state snapshot, buffer changes until it arrives, then replay them. Reply IDs correlate commands. Bounded event queue, snapshot/auth/command timeouts, ping frames, jittered exponential reconnect capped at 30 seconds. Invalid authentication stops retries. REST executes services and tests authentication. Standard TLS validation is never bypassed; HTTP is allowed for deliberately configured local servers.
- `LauncherViewModel.kt`: Activity onStart/onStop owns subscriptions. No receiver, alarm, service, worker or wake lock. Forecast refresh runs every 30 minutes only during an active authenticated session. Settings persist independently of HA availability; app launching works offline.
- `camera/CameraPlayer.kt`: automatic HA-native WebRTC or an explicit go2rtc endpoint with local WebView SDP negotiation, no external scripts and HA-supplied ICE configuration; after a decoded-frame timeout, HLS via Media3 with decoder fallback, bounded buffers and stream renewal. TextureView/zoom fills and clips to the camera card. Failed HLS uses explicitly labeled five-second snapshots while retrying. The HA camera/stream command obtains an HLS URL when no explicit endpoint is supplied. HA bearer headers are attached only to the exact HA origin, never to arbitrary camera endpoints. Players/WebViews are released on disposal and when stopped. Dashboard previews default on with one feed when no count is saved, and allow at most four selected feeds; opening fullscreen disposes previews.
- `ui/`: shared TV surfaces, dashboard, Canvas Sankey and remote-friendly settings. Live HA controls wait for authoritative state updates; mock controls update local demo state only. Unavailable devices are disabled.

Power sensors report W/kW/MW. Today consumption is calculated only from HA recorder change statistics converted to kWh, using midnight in HA’s time zone. The home meter is authoritative, and individual appliance measurements may update at different times. Unknown statistics remain unknown; no lifetime meter reading is substituted for Today.

Camera compatibility depends on Android WebView codecs, device video decoders, LAN routing and the HA camera integration. HA-native WebRTC uses camera/capabilities, camera/webrtc/get_client_config and camera/webrtc/offer subscriptions. Answers and remote ICE candidates are routed separately from state events; unsubscribe and disconnect close the session. Local candidates are queued until the HA session ID arrives, then sent through camera/webrtc/candidate, including later candidates. Remote candidates without a mid/index receive the first remote SDP mid, matching HA’s frontend. Explicit go2rtc HTTP SDP endpoints override discovery; unsupported HA versions fall back to HLS. The launcher does not hardcode STUN/TURN services; optional ICE servers come from HA. Explicit HTTP SDP endpoints gather candidates before posting because they have no trickle channel. A decoded-frame watchdog replaces connected-but-empty or stalled WebRTC with HLS. Safe fixed transport/error codes are logged without SDP, signed stream URLs or tokens. Each WebView lifecycle run has a generation ID so stopped pages cannot send signaling into a newer session.


## Temporary phone setup

`phone/PhoneSetupCoordinator.kt` owns the ten-minute session and a draft. A LAN-only `LocalSetupServer` serves the two bundled assets and a single encrypted API endpoint. The server supports a strict, bounded HTTP/1.1 subset, two IO workers and a two-socket queue; it uses no Android Service. Socket binding/reads run off Main; coordinator mutations and apply callbacks run on Main. Closing Settings, Activity.onStop, expiry or successful apply closes sockets, cancels jobs and wipes the pairing key. Startup cancellation also closes partially opened listeners.

`PairingCrypto.kt` uses standard JCA AES-256-GCM. The 32-byte key travels only in the QR's fragment; the browser uses the bundled MIT-licensed noble-ciphers implementation so encryption works on a local HTTP page without WebCrypto's secure-context requirement. Fresh 12-byte IVs, separate request/response AAD and a per-session nonce set prevent replays and response swapping. Host/Origin allowlisting protects against cross-site requests and DNS rebinding. Loopback aliases are accepted only for loopback peers, for local ADB forwarding/testing.

Pairing binds one random browser ID and requires a matching-code confirmation on the TV. Until approval the API exposes no configuration or HA access. Connection testing reads `/api/states` with a bounded 8 MiB response and retains credentials in RAM; it never calls HA service actions. Selected IDs, domains, units, installed-app IDs, counts and URLs are validated before applying. The API never returns the saved HA token. One apply commits preferences and any new encrypted token together and reconnects normal HA subscriptions.

The initial HTML/JavaScript is local HTTP, so encryption does not authenticate the bootstrap against an active LAN attacker. This feature assumes a trusted private LAN, not a hostile network. See [security model](PHONE-SETUP.md#security-model). No cloud relay, certificate-warning bypass or mandatory Google Play Services is used.

## Room and calendar discovery

`data/HomeCatalog.kt` models area/entity/device registries. Entity area wins over device area, with a naming/attribute fallback if registry permissions are denied. Preferred area temperature/humidity sensors are prioritized; hidden, disabled and diagnostic entities are excluded. Room controls use entity IDs and supported feature flags. No HA registry or dashboard is modified.

Calendar REST requests run only while Calendar is composed and authenticated, with at most three concurrent requests, a 2 MiB per-calendar bound, seven-day horizon and fifteen-minute refresh. Failures are isolated per calendar. All-day dates use HA’s time zone, including DST boundaries. Leaving the page cancels refresh; no background calendar worker is created. Scenes use the live state snapshot automatically; unknown means never-activated for scenes and does not disable them.

Calendar and camera coroutines use `StartedEffect` (`repeatOnLifecycle(STARTED)`) to cancel work directly on lifecycle changes, independently of recomposition. HLS players stop and WebRTC peers/signaling close from lifecycle observers; foreground entry restarts playback. A native test backgrounds the Activity while the frame clock is paused and verifies work stops and restarts on return.

## Today energy and Home camera configuration

`data/LoadEnergy.kt` parses read-only HA Energy preferences, resolves configured meter pairs (including unambiguous same-device/suffix fallbacks), applies optional overrides and excludes nested meters from double counting. `LauncherViewModel` exposes distinct load plans and only relevant live power states. Recorder requests are bounded to 41 IDs, five-minute changes in kWh, local midnight to now, and cached/refreshed at five-minute intervals only while a Today card is visible. Missing data is not synthesized from cumulative meter states. The Gallery Home summary shows up to three named loads and a remaining-consumption row (whole-home minus the displayed loads, including any unlisted appliances). A missing displayed reading or inconsistent negative residual keeps that remainder unknown. Without a home meter, extra mapped appliances use a labelled aggregate. Details retains all measured loads and their full-meter residual.

Config stores homeCameraCount (0–4) and the ordered camera list. Parsing legacy config removes the heating widget, preserves selected camera order/URLs and enables the new live default once. Explicit later preview opt-outs persist. Zero excludes the Home camera panel; fullscreen removes all preview composition. Camera settings are available through the existing TV and encrypted phone draft/apply workflows.

The TV camera settings section exposes the existing validated Save action at its top and bottom, with a draft-versus-saved indicator. Count, camera order and endpoint changes can be committed without returning to main Settings. The native regression test uses D-pad Select to save one feed, reloads a fresh ViewModel from preferences after Activity recreation and verifies only the first selected camera is rendered.

## Gallery Grey 0.5

`ui/GalleryHome.kt` holds the foreground-only clock/weather tile and horizontally navigable scene/light shelves. `Dashboard.kt` has a flat grey shell with a colored icon rail and no global branding/header row. Default widget proportions follow the selected Gallery mockup while respecting saved within-row widget order and camera count. Selecting clock/weather opens the original hourly/daily forecast in a dismissible dialog. App dock sizing fits six banners plus All apps at the default 16:9 width; longer app lists scroll. Installed artwork is used; demo banners use text and service colors without bundled third-party logos.

Shared Tiles use grey selected/focused fills, a white focus outline and colored content icons. Camera callbacks report actual rendered/ready playback; only that state displays Live. Stream startup, errors and snapshots do not. Native tests check two simultaneous real HLS fixtures report live and clear the flag on disposal. No synthetic garden photograph is shown as a live camera in demo.

Camera Settings entry focuses the count controls after layout, with focus handed to the enabled counterpart at zero/four. Existing explicit Save and persistence behavior remains; only missing/new camera-count defaults migrate to one. Other UI proposal phases remain separate from the implemented Home layout and shared styling.
